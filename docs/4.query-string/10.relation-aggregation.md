# Relation aggregation (`:@join`)

[Aggregating](/query-string/aggregating) covers columns on the base model. To aggregate or group by a **related** model's column instead, append `:@join` to an aggregate item — it adds a real SQL `LEFT JOIN` to the related table rather than a subquery.

```
GET /api/authors?aggregate=posts:@count:@join
```

```sql
SELECT COUNT("post"."id") AS "posts_count" FROM "author" LEFT JOIN "post" ON "post"."author_id" = "author"."id"
```

The field before `:@count`/`:@sum`/etc. is a **relation name** declared in `aggregateBy()`, not a column — Curio resolves it on the model to find the join keys and the related table.

```php
public function aggregateBy(): array
{
    return ['name', 'posts'];
}
```

## Supported relations

Only `belongsTo`, `hasOne`, and `hasMany` are supported:

| Relation type                                    | Result                                                                                                                                                |
|--------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------|
| `belongsTo`                                      | Joins the owning side (`LEFT JOIN parent ON parent.id = child.parent_id`)                                                                             |
| `hasOne`                                         | Joins the related table on the foreign key — safe because a `hasOne` returns at most one related row                                                  |
| `hasMany`                                        | Joins the related table on the foreign key — safe because the aggregate/`GROUP BY` collapses the duplicated parent rows the one-to-many join produces |
| `belongsToMany` (many-to-many)                   | **Not supported** — would need an extra pivot join; use `include=relation:@count` instead                                                             |
| Polymorphic (`morphTo`, `morphOne`, `morphMany`) | **Not supported** — a join would be missing the required `*_type` predicate                                                                           |

Attempting `:@join` on an unsupported relation throws a `ValidationException` with an explanatory message rather than producing broken SQL.

## Combining with a group key

Without a `:@group` item in the same `aggregate=` string, `:@join` produces a single-row grand total (no `GROUP BY`). Add a base-model `:@group` field to get one row per group:

```
aggregate=name:@group posts:@count:@join
```

```sql
SELECT "author"."name", COUNT("post"."id") AS "posts_count"
FROM "author"
LEFT JOIN "post" ON "post"."author_id" = "author"."id"
GROUP BY "author"."name"
```

Because it's a `LEFT JOIN`, an author with zero posts still appears in the results, with `posts_count` = `0`.

## Composes with `:@alias`, `:@having`, and `distinct`

```
aggregate=posts:@count:@join:@alias(total)
aggregate=name:@group posts:@count:@join:@having(>=2)
aggregate=posts:@count(distinct:title):@join
```

The last example produces `COUNT(DISTINCT "post"."title")`.

## Grouping by a related column

`:@group` can also target the related table itself — `relation:@group(column):@join` groups by a column on the *related* model, joined via the same shared `LEFT JOIN` as any other `:@join` item on that relation:

```
GET /api/authors?aggregate=posts:@group(status):@join posts:@count:@join
```

```sql
SELECT "post"."status", COUNT("post"."id") AS "posts_count"
FROM "author"
LEFT JOIN "post" ON "post"."author_id" = "author"."id"
GROUP BY "post"."status"
```

Here `relation` (`posts`) is the same on both items, and `column` (`status`) is a plain column name on the related table — not itself validated against `aggregateBy()`, since it never refers to the base model.

## Restrictions

- **Only one relation can be joined per request.** Sending two different `:@join` items (e.g. `posts:@count:@join comments:@count:@join`) fails validation — this includes a `:@group(...):@join` item and an aggregate `:@join` item that target two different relations.
- **`aggregate=` conflicts with sorting by a relation column.** Combining `aggregate=posts:@count:@join` (or any grouped aggregate) with `sort=author.name` fails validation: an aggregated query returns one row per group, not per parent, so there is no parent row for the sort to look its related column up from. A plain (non-relation) `sort=`, including by an aggregate's own alias, is unaffected.
- `@count` without a relation name (`@count:@join` or `*:@count:@join`) is invalid — `:@join` always needs a relation to join.
- `@sum`/`@avg`/`@min`/`@max` still require a column argument when joined (`posts:@sum(views):@join`), same as the base-model form.
