# Default-scoped relations

The `Comment` endpoint (`GET /api/comment`) shows a common pattern: an endpoint that should exclude certain rows by default, without permanently hiding them from every caller.

```php
class CommentQuery extends PaginateQuery
{
    public function includeBy(): array
    {
        return [
            'author' => AuthorQuery::class,
            'post' => PostQuery::class,
        ];
    }

    public function filterBy(): array
    {
        return [
            'title' => ['string'],
            'content' => ['string'],
            'excluded' => ['boolean'],
            'author_id' => ['integer'],
            'post_id' => ['integer'],
        ];
    }

    public function sortBy(): array
    {
        return ['id', 'title', 'excluded'];
    }

    public function defaultSort(): string
    {
        return 'id';
    }

    public function defaultFilter(): string
    {
        return 'excluded:false';
    }
}
```

`defaultFilter()` returns `'excluded:false'`, applied whenever the request doesn't send a `filter` parameter at all:

```
GET /api/comment
```

only returns non-excluded comments. A caller that explicitly wants excluded comments included overrides it by sending their own `filter`:

```
GET /api/comment?filter=excluded:true
GET /api/comment?filter=title:*spam*
```

Note that `defaultFilter()` only applies when `filter` is **entirely absent** from the request — it's not merged with an incoming `filter` value. Sending any `filter=` replaces the default outright, so an endpoint relying on this pattern to hide rows by default should document that callers who filter explicitly are opting out of the exclusion, not adding to it.

This is also the pattern to reach for with soft-delete-like flags (`excluded`, `archived`, `hidden`) where "hidden by default, visible on request" is the desired behavior — as opposed to a scope baked permanently into the underlying `Builder`, which no `filter=` value could override.
