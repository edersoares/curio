# Blog API walkthrough

The `Post` endpoint (`GET /api/post`) exercises most of Curio's query language against a single resource: nested `includeBy`, `filterBy`, a relation `sortBy`, field aliases, and a custom `defaultSort()`.

```php
class PostQuery extends PaginateQuery
{
    public function includeBy(): array
    {
        return [
            'author' => AuthorQuery::class,
            'comments' => CommentQuery::class,
        ];
    }

    public function filterBy(): array
    {
        return [
            'id' => ['integer'],
            'title' => ['string'],
            'content' => ['string'],
            'published_at' => ['date'],
            'author_id' => ['integer'],
            'status' => [],
        ];
    }

    public function sortBy(): array
    {
        return ['id', 'title', 'published_at', 'author.name'];
    }

    public function aggregateBy(): array
    {
        return ['posts', 'posts.status'];
    }

    public function replaceBy(): array
    {
        return [
            'author' => 'author.name',
            'author_name' => 'author.name',
            'author-name' => 'author.name',
            'authorName' => 'author.name',
            'published-at' => 'published_at',
            'publishedAt' => 'published_at',
        ];
    }

    public function defaultSort(): string
    {
        return 'title';
    }
}
```

A few things worth noting:

- **`includeBy()` links to other `PaginateQuery` classes** (`AuthorQuery`, `CommentQuery`), so `include=comments:@filter(excluded:false)` validates `excluded:false` against `CommentQuery::filterBy()`, not `PostQuery::filterBy()`.
- **`replaceBy()`** lets `filter=author:jane` and `filter=authorName:jane` both resolve to the relation column `author.name`, and lets clients use `published-at`/`publishedAt` instead of the snake_case `published_at`.
- **`aggregateBy()`** is declared, but with names (`posts`, `posts.status`) that describe a `posts` relation `Post` doesn't have — its relations are `author` and `comments`. No `aggregate=` works on this endpoint as it stands; the [Author endpoint](/cookbook/relation-aggregation-in-practice), where `posts` is a real relation, is the one to look at for aggregates.

The request is wired to a `FormRequest` and controller exactly as shown in the [quick start](/quick-start):

```php
class PostPaginateRequest extends FormRequest
{
    use PaginateRequest;

    public function getPaginateQuery(): string
    {
        return PostQuery::class;
    }
}

class PostPaginateController
{
    public function __invoke(PostPaginateRequest $request): PostResourceCollection
    {
        return new PostResourceCollection(
            $request->paginate(Post::query())
        );
    }
}
```

And the resource reads eager-loaded relations and relation aggregates directly, through Laravel's own `whenLoaded()`/`whenCounted()`/`whenAggregated()`, alongside the `AggregateResource` trait:

```php
class PostResource extends JsonResource
{
    use AggregateResource;

    public function toArray(Request $request): array
    {
        return [
            'id' => (int) $this->id,
            'author_id' => (int) $this->author_id,
            'title' => $this->title,
            'content' => $this->content,
            'published_at' => $this->published_at,
            'status' => $this->status,
            'category' => $this->category,
            'author' => AuthorResource::make($this->whenLoaded('author')),
            'comments' => CommentResourceCollection::make($this->whenLoaded('comments')),
            'comments_count' => $this->whenCounted('comments'),
            'comments_sum' => $this->whenAggregated('comments', 'author_id', 'sum'),
        ];
    }
}
```
