# Relation aggregation in practice

This example ties together [relation aggregation](/query-string/relation-aggregation) and [casting](/query-string/casting) against the blog domain's `Author`/`Post` relationship.

## Counting each author's posts via `:@join`

Given `AuthorQuery::aggregateBy()` includes `'posts'`:

```
GET /api/author?aggregate=name:@group posts:@count:@join
```

```sql
SELECT "author"."name", COUNT("post"."id") AS "posts_count"
FROM "author"
LEFT JOIN "post" ON "post"."author_id" = "author"."id"
GROUP BY "author"."name"
```

Because the join is a `LEFT JOIN`, authors with zero posts still appear in the results with `posts_count: 0` — unlike an `INNER JOIN`, which would silently drop them.

## Compared to `include=posts:@count`

`PostResource`'s sibling pattern — `whenCounted('comments')` fed by `include=comments:@count` — solves a related but different problem: it adds a `withCount` **without collapsing rows**, so you still get one row per `Post` with a `comments_count` column attached. `aggregate=...:@join`, by contrast, **replaces** the result set with grouped rows — one row per `author.name`, not one row per author. Reach for `include=relation:@count` when you want the parent rows intact with a count attached; reach for `aggregate=...:@join` when you want the grouped/rolled-up view instead.

## Combining with a cast

The `posts_count` column produced by the aggregate above isn't declared through `castBy()`/`castMutator()` — it's a normal aggregate output column, not a cast. But nothing stops combining an `aggregate=` request with a `cast=` on a base-model field in the same request, since they're independent parameters:

```
GET /api/author?aggregate=name:@group ranking:@group posts:@count:@join&cast=ranking:@rankingTier
```

This groups by both `name` and `ranking`, counts each group's posts via the joined relation, and — because `ranking` is also selected as a passthrough `@group` column — lets `cast=ranking:@rankingTier` derive a tier label from it in the same response.
