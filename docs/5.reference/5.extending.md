# Extending Curio

Every fluent DSL call (`filter()`, `sort()`, `select()`, `aggregate()`, `include()`, `cast()` — whether from `Model::curio()` or through the HTTP pipeline) parses its argument immediately and queues the result; nothing touches the query builder until a terminal call (`get()`, `paginate()`, `first()`, ...) actually runs.

At that point the whole batch goes through `Dex\Laravel\Curio\Pipeline`, which first dispatches one `Dex\Laravel\Curio\Events\ApplyPending` event carrying every queued token, and then runs its own steps in a fixed order — field-alias resolution via `replaceBy()`, one step per DSL type, and registering relation-aggregate/include aliases as sortable.

It's a normal Laravel event, so your own application can hook a listener onto it too — for auditing, metrics, or rewriting a request before it is applied:

```php
use Dex\Laravel\Curio\Events\ApplyPending;
use Illuminate\Support\Facades\Event;

Event::listen(ApplyPending::class, function (ApplyPending $event) {
    Log::info('curio query', [
        'model' => $event->builder->getModel()::class,
        'types' => array_unique(array_column($event->tokens, 'type')),
    ]);
});
```

## What the event carries

| Property          | Type                    | Notes                                                                                                                                                                                                                    |
|-------------------|-------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `$event->tokens`  | array of parsed clauses | Every token queued since the last dispatch, each tagged with its own `type` (`filter`, `sort`, `select`, `aggregate`, `include`, or `cast`). Mutable — a listener can rewrite it in place before it is applied.          |
| `$event->builder` | `Builder\|Relation`     | The Eloquent builder (or relation, for a nested/scoped context) being queried.                                                                                                                                           |
| `$event->query`   | `PaginateQuery`         | The bound query class, or a synthesized adapter over the model's own `YourCuriosity` methods on the unbound (`Model::curio()`) path.                                                                                     |

## A hook, not the mechanism

Curio's own steps are not listeners on this event — `Pipeline` calls them directly, right after dispatching it. That has two consequences worth knowing:

- **Your listener runs before anything is applied.** It sees the tokens exactly as they were parsed, with `replaceBy()` aliases not yet resolved, and the builder untouched. Whatever it leaves in `$event->tokens` is what gets applied — after going through the same allow-list validation as any other token.
- **A listener can't switch the pipeline off.** Filters, validation and `defaultFilter()` are applied whether or not the event was delivered: under `Event::fake()`, or when a listener returns `false` (which stops the dispatcher from calling the listeners after it), the query is still built in full. A filter that is silently skipped returns more rows than the caller asked for, so applying it never depends on the dispatcher.

`Dex\Laravel\Curio\Events\ApplyToken` works the same way one level down: it is dispatched once per key/value filter clause (including each clause nested under a relation), before that clause becomes a `where*()` call, and a listener may rewrite `$event->token`.

To change the steps themselves — add one, drop one, reorder them — extend `Pipeline` and bind your subclass in the container:

```php
use Dex\Laravel\Curio\Pipeline;

class AppPipeline extends Pipeline
{
    protected const array PENDING = [
        ...parent::PENDING,
        AuditStep::class, // any class with a `handle(ApplyPending $event)` method
    ];
}

$this->app->bind(Pipeline::class, AppPipeline::class);
```
