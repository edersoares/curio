# API resources

Two traits glue Curio into Laravel's request/resource layers: `PaginateRequest` on the `FormRequest` side, `AggregateResource` on the `JsonResource` side.

## `PaginateRequest`

`Dex\Laravel\Curio\Extensions\PaginateRequest` is a trait for a `FormRequest` (`@mixin FormRequest`). It's the piece wired up in the [quick start](/quick-start):

```php
class PostPaginateRequest extends FormRequest
{
    use PaginateRequest;

    public function getPaginateQuery(): string
    {
        return PostQuery::class;
    }
}
```

| Method | Purpose |
|---|---|
| `getPaginateQuery(): string\|PaginateQuery` | Abstract — return the `PaginateQuery` subclass's class name (resolved through the container), or an instance already configured for this request. The only method you must implement. |
| `rules(): array` | Generates the request's validation rules from the `PaginateQuery` (`filter`, `include`, `sort`, `aggregate`, `cast`, `page`, `size`), merged with `additionalRules()`. |
| `additionalRules(): array` | Override to merge in extra validation rules for non-Curio inputs on the same endpoint. Empty by default. |
| `allowedFilter()` / `allowedInclude()` / `allowedSort()` / `allowedAggregate()` / `allowedCast()` | Individually overridable per-section rule builders — each returns `[]` (no rule at all) when the corresponding `*By()` method is empty, and a `['string']` rule (or, for `aggregate`, `['string', 'prohibits:select']`) otherwise. |
| `paginate(Builder $builder): LengthAwarePaginator` | Runs the full pipeline — resolve params, parse, validate, apply, paginate — via the `Paginator` service. |

`allowedAggregate()`'s generated rule includes Laravel's `prohibits:` rule against the configured `select` parameter name, which is how `aggregate=`/`select=` are enforced as mutually exclusive at the validation layer.

## `AggregateResource`

`Dex\Laravel\Curio\Extensions\AggregateResource` is a trait for a `JsonResource` (`@mixin JsonResource`) that surfaces `aggregate=`/`cast=` output alongside normal resource attributes.

```php
class AuthorResource extends JsonResource
{
    use AggregateResource;

    public function toArray(Request $request): array
    {
        return [
            'id' => $this->id,
            'name' => $this->name,
        ];
    }
}
```

| Method | Purpose |
|---|---|
| `resolve($request = null)` | Short-circuits to the model's raw attributes (`$this->resource->getAttributes()`) whenever the request's `aggregate` query parameter is present — since an aggregated row generally doesn't map onto the resource's normal `toArray()` shape (grouped/derived columns instead of full model attributes). |
| `toAttributes(Request $request): array` | Appends two keys to the resource output: `aggregates` (heuristically detected `*_count`/`*_exists`/`*_sum`/`*_avg`/`*_min`/`*_max` attributes present on the model) and `casts` (the model's `casts` attribute, written by [Casting](/query-string/casting)). Both are wrapped in `when()`, so they're omitted entirely when empty. |

```json
{
  "id": 1,
  "name": "Jane",
  "aggregates": {
    "posts_count": 4
  },
  "casts": {
    "ranking": "bronze"
  }
}
```

> `AggregateResource`'s `aggregates()` detection is a naming-pattern heuristic (matching `_count`/`_exists`/`_sum`/`_avg`/`_min` /`_max` in the attribute key) because `withCount`/`withSum`/etc. write plain, unmarked attributes onto the model — there's no other signal available at the resource layer to distinguish them from real columns. `casts()` doesn't need this, because `Casting::applyParsed()` always collects its output into one dedicated `casts` attribute rather than the field's own attribute.

Using `AggregateResource` is optional, and it doesn't replace Laravel's own helpers: a resource can read `whenCounted()`/`whenAggregated()` directly, with or without the trait. This package's own `PostResource` does both — see [the blog API walkthrough](/cookbook/blog-api-walkthrough).
